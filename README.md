# ChatGPT 模型路由检测器

当前版本：`1.1.2`  
项目状态：可测试的早期版本，仅支持手动加载

这是一个用于 Chrome 和 Edge 的 Manifest V3 浏览器扩展。它在每次 ChatGPT 对话请求中读取客户端请求的模型，并与响应中公开的服务端模型路由元数据进行核对，然后在页面右下角显示本轮结果。

本项目的目标很具体：帮助用户确认“浏览器请求的模型名称”和“服务器返回给浏览器的模型标注”是否一致。它不是回答质量评估器，也不是对 OpenAI 后台实际运行模型的独立鉴定工具。

> 本项目与 OpenAI 没有隶属或官方合作关系。ChatGPT 的网页内部接口并非稳定、公开的开发接口，因此扩展可能随网页改版暂时失效。

## 能做什么

- 在 `https://chatgpt.com/*` 页面自动运行；
- 按每一次发送、重新生成或继续生成分别建立检测记录；
- 核对客户端 `request.model` 与服务端 `server_ste_metadata.model_slug`；
- 使用 assistant metadata、resolved model、页面 DOM 等字段作辅助校验；
- 区分“对应”“不对应”“待确认”和“无法检测”，避免把缺少数据误报为模型不对应；
- 展示不含聊天正文的诊断摘要，便于排查兼容性问题；
- 全程在当前浏览器页面本地处理，不建立账号或后台服务器。

## 不能证明什么

扩展观察到的仍然是浏览器可见数据。它可以说明：

```text
请求体中的模型字段
        与
服务端返回给网页的模型路由元数据
是否一致
```

它不能证明 OpenAI GPU 实际加载了哪一份模型权重，也不能证明：

- 服务端公开的模型元数据一定完整、准确；
- 回答质量高低是否源于模型切换；
- 出现未知字段、缺少字段或解析失败就代表“降智”。

因此，扩展给出的结论应理解为**网页可见模型路由元数据的一致性结果**，而不是后台模型的审计结论。

## 安装

本项目目前没有发布到 Chrome Web Store 或 Edge Add-ons，需要以“已解压的扩展”方式安装。

1. 在 GitHub 仓库页面点击 **Code → Download ZIP**，并将压缩包完整解压。
2. Chrome 打开 `chrome://extensions/`；Edge 打开 `edge://extensions/`。
3. 开启“开发者模式”。
4. 点击“加载已解压的扩展”。
5. 选择包含 `manifest.json` 的项目根目录，而不是单独选择 `content` 文件夹。
6. 打开或刷新 `https://chatgpt.com/`，发送一条消息进行测试。

扩展本身没有登录流程，也不会取得或保存 ChatGPT 登录凭据。能否使用 ChatGPT 对话由 ChatGPT 页面自身决定；只有页面真正发起对话请求后，扩展才有数据可检测。

## 使用

安装并刷新 ChatGPT 后，页面右下角会出现“模型检测”状态卡。

- 未发送消息时，卡片表示检测器已经就绪；
- 发送消息后，卡片显示本轮请求和响应的采集进度；
- 获得足够证据后，卡片显示判定结果；
- 点击卡片可以展开原始字段、判定理由和诊断摘要；
- 点击“复制诊断”可以复制当前轮次的排查信息。

重新生成回答、继续生成以及切换模型后的新请求均视为新轮次。页面只显示最近一次有效发起的轮次；旧轮次迟到的网络事件不会把卡片切回旧结果。

## 如何理解检测结果

| 状态 | 含义 | 应如何处理 |
| --- | --- | --- |
| `模型对应` | 两个主模型字段完全相同，或命中人工确认的合法映射 | 可以确认网页可见的请求与路由标注相符 |
| `模型不对应` | 命中人工确认的不兼容模型对 | 展开卡片核对原始证据；不要仅凭红色状态推断后台行为 |
| `待确认` | 名称不同但映射未知，或主/辅助证据存在冲突 | 需要结合原始字段进一步确认，不能直接视为不对应 |
| `检测中` | 已观察到请求，仍在等待响应或延迟到达的模型元数据 | 等待回答完成及最多 6 秒的延迟元数据窗口 |
| `无法检测` | 本轮缺少关键字段，或请求/响应解析未完成 | 查看具体原因并复制诊断 |
| `模型检测` | 尚未观察到新的对话请求 | 正常发送一条消息；这不是故障状态 |

判定遵循保守原则：

1. 主字段完全一致，可判定为“模型对应”；
2. 主字段不同，只有命中明确配置的合法映射时才判定为“模型对应”；
3. 只有命中明确配置的不兼容模型对时才判定为“模型不对应”；
4. 名称不同但关系未经确认时，一律显示“待确认”；
5. 缺少关键证据时显示“无法检测”，不以缺失数据推断不对应；
6. 同一证据字段出现多个不同值时保留冲突，不用后到值静默覆盖先到值。

当前 `content/model-rules.js` 中的默认映射表为空。因此，除主字段完全相等外，不会仅凭模型名称相似、前缀相同或属于同一系列而自动判绿；初始版本也不会在没有明确规则的情况下判红。

## “无法检测”的具体原因

| 页面提示 | 实际含义 | 常见情况 |
| --- | --- | --- |
| `请求无模型` | 捕获到了对话请求，但未取得请求中的 `model` | 请求结构变化或请求体格式暂不支持 |
| `未捕获响应` | 捕获到了请求，但在 30 秒内没有观察到对应响应 | 网络失败、页面中断或接口流程变化 |
| `响应无模型` | 响应正常结束，但没有取得服务端模型字段 | 服务端本轮未提供字段或字段位置变化 |
| `响应中断` | 响应读取被取消、导航打断或发生读取错误 | 刷新、停止生成、关闭页面或网络中断 |
| `格式不支持` | 收到了非空响应，但现有解析器无法识别 | ChatGPT 更改了响应格式 |

回答结束后，扩展会在同一个 6 秒窗口内接收可能延迟到达的 telemetry 元数据。在窗口结束前，若服务端模型字段尚未到达，状态会保持“检测中”，并明确显示“等待延迟模型元数据”；字段一到就立即判定。完整窗口结束后仍缺少关键字段，才会显示“无法检测”。辅助字段显示“未提供（可选）”也不等于检测失败。

如果状态长期不更新或频繁无法检测：

1. 确认扩展页面显示的版本为 `1.1.2`；
2. 在扩展管理页面点击“重新加载”；
3. 完整刷新 ChatGPT 页面后重新发送一条消息；
4. 展开右下角卡片并点击“复制诊断”；
5. 提交问题时附上诊断文本、复现步骤和页面截图。

诊断文本中的事件数、JSON 载荷数、解析异常数和响应字节数用于区分“没有捕获”“捕获但没有字段”和“响应格式无法解析”。

## 采集字段与证据权重

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `request.model` | 对话请求体 | 主证据：客户端请求模型 |
| `server_ste_metadata.model_slug` | 服务端响应或可唯一关联的 telemetry | 主证据：服务端公开路由标注 |
| `metadata.model_slug` | assistant 消息元数据 | 辅助交叉验证 |
| `resolved_model_slug` | 服务端响应元数据 | 辅助交叉验证 |
| `data-message-model-slug` | 当前 assistant DOM 节点 | 辅助交叉验证 |
| `requested_model_experience` | 服务端元数据 | 补充展示，不单独决定对应关系 |
| `request.thinking_effort` | 对话请求体 | 补充展示，不单独决定对应关系 |

主字段和辅助字段不会被等权投票。辅助字段冲突会让结论降级为“待确认”，但不会自行产生“模型不对应”的结论。

快速连续发起多个请求时，只有能够唯一关联到某一轮的 telemetry 才会被采用；存在多个可能轮次时会丢弃该条辅助证据，以避免串轮。普通 telemetry 中孤立的 `metadata.model_slug` 不会被提升为服务端主证据。

## 隐私与权限

- 仅申请 `https://chatgpt.com/*` 的站点权限；
- 不申请浏览历史、标签页、Cookie 或本地存储权限；
- 不建立外部服务器，不上传检测记录，也不主动向第三方发送网络请求；
- 不保存检测历史，刷新页面后当前记录清除；
- 不转发请求 URL、请求头、账号信息、聊天正文或附件；
- 不监听输入框或发送按钮；
- 响应扫描会跳过 `content`、`parts`、`text`、`messages`、`attachments`、`files`、`prompt` 和 `body` 等正文树；
- 页面通信只传递经过长度限制的模型相关标量及有界的解析/生命周期计数。

为了观察 ChatGPT 页面自身发出的请求，采集桥运行在网页的 MAIN world；判定逻辑和界面运行在扩展的 ISOLATED world。两者通过受限的 `window.postMessage` 消息通信。MAIN world 与网页共享 JavaScript 环境，因此理论上可能受到网页改动或干扰，这也是本项目无法提供强审计保证的原因之一。

复制诊断目前包含模型字段、扩展版本、请求/响应状态、响应格式、结束原因、受限计数、本地轮次编号和相对耗时，不包含绝对时间、内部请求 ID 或聊天正文。提交前仍建议自行检查剪贴板内容。

## 更新扩展

以“加载已解压的扩展”安装的版本不会从 GitHub 自动更新。更新步骤如下：

1. 下载新的项目文件并覆盖或替换旧目录；
2. 打开 `chrome://extensions/` 或 `edge://extensions/`；
3. 点击本扩展的“重新加载”；
4. 刷新已经打开的 ChatGPT 页面；
5. 在复制诊断中确认扩展版本。

## 技术实现

扩展在 `document_start` 阶段加载，并将职责分为三部分：

- `content/detector.js`（MAIN world）：包装同源的 `fetch`、XHR 和 `sendBeacon`，识别 ChatGPT 对话与 telemetry 请求，解析 SSE/JSON 响应，并只发出模型字段及受限诊断数据；
- `content/content.js`（ISOLATED world）：维护每轮状态、接收证据、读取受限 DOM 属性、执行判定并渲染状态卡。
- `content/timing.js`：同时加载到两个 world，提供唯一的延迟模型元数据等待窗口，避免采集端与界面端的时间策略不一致；

解析器支持当前测试覆盖到的：

- `/backend-api/f/conversation`；
- `/backend-api/conversation`；
- 上述路径的后缀和查询参数变体；
- `fetch` 与 XHR；
- SSE 流、普通 JSON、多行 JSON 和 JSON 数组；
- `LF`、`CRLF` 和单独 `CR` 换行；
- 常见的 `server_ste_metadata` 嵌套形式；
- 回答正文中看似模型元数据的 JSON 文本隔离。

这些兼容项来自现有实现与自动化测试，不代表对 ChatGPT 未来接口的承诺。

```bash

```

自动化测试不能替代真实页面测试：本项目依赖 ChatGPT 私有网页接口，发布前仍需在实际 Chrome/Edge 和真实 ChatGPT 对话中进行验收。

## 修改模型映射规则

规则位于 `content/model-rules.js`：

- `equivalent`：已核实的合法“请求模型 → 服务端模型”组合；
- `incompatible`：已核实的不兼容“请求模型 → 服务端模型”组合。

规则是有方向的，反向关系需要单独配置。只有在多次真实样本和辅助字段能够支持结论时才应加入规则。不要根据名称相似度、产品名称或单次截图猜测映射。

修改规则后至少应补充 `test/verdict.test.js`，运行全部测试，并重新进行真实页面验收。

## 已知限制

- 当前只支持 `chatgpt.com`，不支持其他域名或第三方 ChatGPT 客户端；
- 当前仅提供开发者模式下的手动安装，没有商店安装包和自动更新；
- 当前不保存历史轮次，状态仅存在于当前页面内存；
- 当前映射表为空，名称不同的模型通常会显示“待确认”；
- 页面刷新、停止生成和网络中断可能产生“响应中断”；
- 多个并发轮次可能使无法可靠归属的 telemetry 被主动丢弃；
- ChatGPT 网页接口或 DOM 改版可能导致暂时“无法检测”；
- 尚未完成覆盖不同账号、地区、模型入口和灰度版本的大规模兼容性验证。

- 扩展版本；

- 是否为新对话、重新生成、继续生成或切换模型后的请求；
